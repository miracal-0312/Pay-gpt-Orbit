# Pay-gpt-Orbit

仅通过 **Orbitcard HMAC V1** 完成 ChatGPT 订阅兑换。提供 CDK 管理、自动选卡、补款与申请卡、订单追踪、重启恢复、持久化审计、管理员认证及 Telegram 通知。

本地支付、卡池、代理池、账单地址、浏览器自动化、验证码求解、支付链接调试和旧版直接订阅管理均已移除。容器只运行 Node.js；生产依赖为 `axios`、`express`、`mysql2`、`ws`，不安装浏览器、Python 或 AI 模型。

[部署与升级](DEPLOY.md) · [完整链路](RECHARGE-AUDIT.md) · [自动选卡与申请卡](ORBITCARD-CARDS.md) · [接口接入](对接api.md) · [Orbitcard 原始协议](orbitcard-subscription-api-v1.md)

## 界面与导航

用户兑换页按「验证卡密 → 提交 Session → 查询结果」显示当前步骤。后台采用侧栏导航，手机上通过左上角菜单切换页面；地址栏仅保留当前功能页标识，刷新后可返回同一页。

兑换页手动查询后继续自动跟踪；每次请求最多等待 30 秒，提交超时或返回结果不明时先查询原订单，不自动重发充值。明确失败且 CDK 已释放时显示「重新验证并继续充值」，重新校验卡密后才开放提交。查询遵守服务端返回的等待间隔。后台历史次数未确认的订单提供登记入口，「卡片与开卡」集中提示待登记卡 ID，点击可定位到对应登记表。

「接口与支付调试」已独立于「Orbitcard 配置」，保留只读查询、分步预检、真实扣款测试和原单链路日志。默认充值地区及接单开关仍在配置页设置。订单、CDK、管理员订单和卡片列表支持搜索当前已加载的数据；搜索不会改变 CSV 导出范围，导出仍按 CDK 套餐筛选。日志支持复制和自动换行切换。

这轮界面更新不新增生产依赖、环境变量或数据库字段。浏览器截图和模拟测试工具不包含在生产镜像中。

## 快速开始

需要 Node.js 24+ 和 MySQL 8；或 Docker Engine 与 Compose V2。

```bash
cp .env.example .env
# 填写数据库密码、管理员密码、随机签名密钥，以及配对的 ORBITCARD_API_KEY / ORBITCARD_API_SECRET
docker compose up -d --build
docker compose logs -f app
```

默认用户入口 `http://localhost:3000/`，管理员入口 `http://localhost:3000/admin-login`。首次创建管理员需要至少 8 位的登录密码、二级密码；`ADMIN_TOKEN_SECRET` 每次启动都必须为至少 32 字节的随机值。

在服务器 `.env` 中配置平台签发且配对的 `ORBITCARD_API_KEY` 和 `ORBITCARD_API_SECRET`，然后重建应用容器。后台只显示凭据是否配置，不接收、回显或保存凭据；之前存于数据库的凭据不再用于请求，两项环境变量齐全后启动时会清除旧记录。后台继续配置 HTTPS 根域名、可选开卡产品、单卡首充上限和服务费上限。各套餐的支付预算只取 `getProductCode` 产品目录中的对应 USD 价格；接口不返回某档价格时停止自动充值，不使用旧后台预算或订阅套餐的 USDT 服务费代替。后台「Orbitcard 配置 → 默认充值地区」可为 Plus、Pro 100、Pro 200、Pro 500 分别选择地区，选项来自 `getSubscriptionPaymentRegions`。选择「平台默认」时省略 `payment_region`；指定地区时在资金操作前校验其可用性，再传给订阅接口。用户兑换、管理员测试和人工交付共用该设置。配置页显示实时读取的卡 ID；推荐价面板和地区价格对照已移除，产品查询及 Python 检查报告不再列出推荐价金额。后台仍使用实时产品数据核对资金和自动补款。连接测试与地区查询提供本页请求摘要；新增「支付链路调试」可执行只读预检、真实测试开通，以及按任务编号读取持久化链路日志。开卡产品码留空时会自动选择，首充 20.00 USD、数量 1 由服务端组装。测试连接后开放接单；账户余额不足时锁定 CDK，旧卡不足补差额，无符合次数条件的卡时首充 20 USD 开新卡。

CDK 管理页从 `getSubscriptionPlans` 实时读取当前 API Key 开放的 ChatGPT 套餐，生成或导入时再次核对目录。所有新 CDK 都是「自助」类型，仅支持 Plus、Pro 100、Pro 200 和 Pro 500。格式为 `YZW-{12位随机字符}-{短套餐代码}`；后缀仅用于辨认，实际套餐由数据库 `plan_type` 决定。人工交付使用同一批自助 CDK，不再生成单独的手动 CDK；历史手动 CDK 数据保留。

裸机部署：

```bash
npm ci --omit=dev --ignore-scripts
# 编辑 .env，并准备有建表和 ALTER 权限的 MySQL 数据库
npm start
```

安装脚本 `sh scripts/install.sh` 或 `powershell -File scripts/install-windows.ps1` 只安装 Node 生产依赖，缺少 `.env` 时复制模板；不覆盖现有配置。Windows 可使用 `npm.cmd`。

## 充值链路

支付核心按「受理 → 准备支付卡 → 提交一次 → 查询原单 → 事务结算」组织。自助兑换和管理员开通共用套餐映射、实时选卡、订阅请求组装及结果归属校验；HTTP 入口不再承载支付循环。仅保留 Plus、Pro 100、Pro 200、Pro 500，既有 CDK、后台管理及审计接口继续使用。

1. 用户验证 CDK，提交目标账号完整 Session JSON。
2. 检查接单开关、维护状态、配置和并发容量。
3. 在 MySQL 事务中锁定 CDK、检查已有任务、创建任务、保存本次唯一 `client_order_no` 并占用 CDK；同一 CDK 的并发请求只会受理一笔新任务。
4. 查询当前套餐并核对是否开放；订阅目录的 USDT 服务费不作为会员支付金额。读取 `getProductCode` 的产品 USD 推荐价后检查账户 `available_balance`；当前套餐缺少价格时停止自动充值，余额不足则锁定 CDK 并提示联系管理员。付款选卡时再从平台拉取卡列表和批量详情，筛选 ACTIVE、USD、资料齐全且当前套餐次数可用的卡；详情缺项跳过该卡，不逐张补查。优先使用合格旧卡，卡余额不足则补到该产品的套餐价格加最低留存余额；没有合格旧卡时固定首充 20 USD 开卡。批量详情整体缺失、卡 ID 归属异常或请求失败时停止选卡，避免误判为空库存而开卡。同一卡 Plus 最多 4 次，Pro 100/200/500 各 1 次，分别计数且可混用。历史卡同步后需确认四档已有次数，新申请卡自动登记。已设置默认充值地区的套餐会在选卡、补款或开卡前查询地区可用性，查询失败或地区不可用时停止；未设置时省略地区参数。已提交的订阅只查询原单，修改默认地区不会重复下单。
5. 选卡后不再逐张复核候选卡。以 MySQL 事务原子认领这笔任务的 `prepared → submitting` 状态；只有认领成功的执行者使用固定 `client_order_no` 作为平台幂等键调用一次 `createSubscription`。补款提交前及确认后仍按原补款意图核对卡片资金，避免重复补款。若管理员配置了服务费上限，仅在下单时传给平台校验。
6. 查询原订单；需要人机验证时，用户通过有时效的上游链接完成验证。平台明确返回订阅成功则核销 CDK、计次并释放卡占用。
7. 只有平台详情明确确认订阅失败，才开启下一笔新订单：每张卡只尝试一次；明确失败后重新读取平台卡片并排除已失败卡，最多换两张不同卡。每次失败保留独立任务、原订单号和结果日志，在事务中释放上一笔卡片预占并创建新的订单身份。第三张卡也明确失败时锁定 CDK，提示客户联系人工售后。提交被拒绝、超时和查询失败不当作可自动重试的支付失败。
8. 重启后自动恢复原单查询，用户也可用原 CDK 手动查询。网络超时或 `submitting` 结果未知时只查原单，不自动再次创建订阅；恢复中明确失败且仍有次数时，会保留 CDK 并要求用户提交同一账号的最新 Session 继续。未确认开卡/补款保留原身份确认，已知补款订单只查原流水。

自动前台跟踪最多 15 分钟，后台继续有间隔地恢复未确认订单。同一 API Key 遇到 HTTP 429 后，所有 Open API 操作共同遵守平台 `Retry-After` 冷却时间。订阅成功后记录卡片和账户资金快照；后台可按卡查询脱敏消费交易用于对账。交易记录不直接决定订阅结果，也不触发自动退款。平台服务费和订阅状态分别记录；`charge_pending` / `charge_failed` 不会把订阅成功改成失败。

自动开卡有明确前提：先处理本任务已有的补款、开卡意图，再考虑其他卡。没有可直接支付的卡时，有合格卡余额不足就补差额；只有暂被其他订单占用的卡、或历史次数未登记的卡时提示等待或登记，不为此另外花钱开卡。没有这些待处理条件，且实时库存中没有符合规则的卡时，才首充 20 USD 开新卡。读取准备记录失败时保留 CDK 和卡片，不能据此判断“没有发生资金操作”。

本次支付核心重构不新增环境变量、依赖或数据库字段。入口与部署方式不变，更新代码后重新构建应用即可；数据库、`.env` 和 `data/logs` 应继续挂载原有持久化目录。

## 管理员上传 Session 开通

后台「手动开通」需要管理员登录并通过二级验证。套餐从 Orbitcard `getSubscriptionPlans` 实时读取，仅显示当前 API Key 开放的 Plus 和三档 Pro。管理员上传 JSON 文件或粘贴完整 Session，选择套餐；提交时才实时调用 `getAccountBalance`、`getProductCode`、`getCardList` 和批量 `cardDetail` 自动选卡。只选择已登记历史次数、ACTIVE、USD、当前套餐次数未满且未占用的卡。卡内余额不足时按差额调用 `rechargeCard`；没有合格卡时调用 `createCard` 首充 20 USD。缺失整批详情或原补款/开卡结果未知时保留原请求待确认。

- **测试开通**：真实调用 `createSubscription` 并从自动选中的卡扣款，不需要或占用 CDK。即使前台新订单开关关闭，已配置凭据的管理员仍可测试。
- **人工交付**：必须输入匹配套餐的未使用 CDK。使用 CDK 管理页统一生成的同套餐自助 CDK。提交前在 MySQL 事务内占用 CDK 和支付卡；平台原单明确成功后核销 CDK，明确失败后释放 CDK。

两种模式都先保存唯一管理员订单，再准备卡片和资金，用固定 `client_order_no` 作为幂等键提交一次。开卡或补款未确认时保留原请求编号；管理员在订单列表点「继续准备」并重新提供 Session，不能创建新的订单。订阅超时、重启或结果不明确时只查询原订阅订单，不再次付款；订阅提交前中断且卡片已准备的订单在两分钟后释放 CDK 和卡片。管理员订单单独展示状态、验证码链接和可下载的持久化日志；Session 不写入订单或日志。历史卡的四档成功次数仍需先核对，未确认历史的旧卡不参与选卡。

管理员订单在 `preparing` / `prepared` 阶段不调用 `getSubscription`。提交后查询校验原平台与 API Key 身份，并按至少 5 秒及平台 `Retry-After` 间隔合并刷新请求。自助订单同样校验已保存的 API Key 身份；切换平台账号后不能用新凭据查询原订单。

| CDK 类型 | Orbitcard 套餐 |
| --- | --- |
| `plus` | `gpt-plus` |
| `pro100` | `gpt-pro-5x` |
| `pro200` | `gpt-pro-20x` |

## 状态与数据

任务、CDK 和订单绑定保存在 MySQL；按日及按任务 JSONL 保存在 `data/logs`，后台可下载。完整 Session、签名和验证码凭据不写入任务数据库或普通日志。验证码链接仅保留在响应和短时内存中。

升级不会删除旧数据库表、历史账单、Session 数据或宿主机文件。历史非 Orbitcard 运行任务转为人工核对并保留 CDK；这些数据不会被重新执行，也不再提供原有支付入口。

### 查询 CDK 是否已核销

`POST /api/cdk/status`，请求头 `Content-Type: application/json`，请求体为 `{"cdk":"你的卡密"}`。持有卡密即可查询，无需管理员登录或提供 Session。

```bash
curl -X POST 'https://你的域名/api/cdk/status' \
  -H 'Content-Type: application/json' \
  -d '{"cdk":"你的卡密"}'
```

已核销时返回 HTTP 200：

```json
{
  "success": true,
  "data": { "status": "redeemed", "redeemed": true },
  "message": "CDK 已核销"
}
```

| `data.status` | `data.redeemed` | 含义 |
| --- | --- | --- |
| `redeemed` | `true` | 已确认充值成功并核销，包含自助兑换和管理员人工交付 |
| `processing` | `false` | 已占用但尚未确认核销，包括处理中、待确认、重试或售后锁定 |
| `unused` | `false` | 未使用或已释放 |

`success` 表示查询成功，不表示充值成功；请以 `data.redeemed === true` 判断已核销。`redeemed: false` 不代表可以再次兑换，应结合 `status` 判断。

接口只读取本地数据库的已保存状态，与后台 CDK 列表一致，不主动向平台查单，也不会发起充值或改变 CDK 状态。平台刚完成充值时，需等待后台查单同步后才会显示已核销。响应不包含账号、Session 或支付资料，并设置 `Cache-Control: no-store`。

CDK 格式错误返回 HTTP 400，不存在或已停用返回 HTTP 404，服务异常返回 HTTP 503；错误响应为 `{"success":false,"message":"错误说明"}`，不返回 `redeemed: false`，避免将查询失败误判为未核销。

## 验证

并发保护分为两层：MySQL 行锁保证 CDK、订单、卡片计次原子结算；数据库连接持有的命名执行锁协调受理、后台支付和恢复查询。自助兑换按 CDK 锁定，管理员订单按请求编号锁定，人工交付同时锁定所用 CDK。锁覆盖异步订阅提交，重复请求只读取原单或返回处理中；恢复任务取锁后重新读取订单状态，不能使用旧快照释放另一执行者的订单。

执行锁和选卡锁使用独立 MySQL 连接，不占用 `DB_POOL_LIMIT` 控制的业务查询连接池。进程退出或连接断开时 MySQL 释放锁；当前执行者在写入资金操作前检查执行权。已经写入的开卡、补款、订阅身份继续保留，由原单恢复流程核对。数据库死锁或锁等待超时仅在确认回滚后重试，最多 3 次；提交结果不明、业务错误和回滚失败不重试，事务内不得调用平台支付接口。

失败或拒绝的旧订单不会被迟到的成功结果重新打开，已绑定的平台订单号不可被另一订单号覆盖；准备阶段的订单不能直接按订阅查询结果结算。本次无需增加环境变量、Redis 或数据库表。部署及连接数限制见 [DEPLOY.md](DEPLOY.md)。

可先用 Python 3.10+ 标准库脚本检查真实 Orbitcard **读取权限与响应字段**。在执行脚本的环境中设置 `ORBITCARD_API_KEY` 和 `ORBITCARD_API_SECRET`，再复制 [配置示例](scripts/orbitcard-openapi-check.example.json) 到仓库外的路径；JSON 只保存非敏感检查参数。`card_id` 留空时自动选列表中的首张卡；有原订单时可填写 `task_no` 或 `client_order_no` 其中一个。运行：

```bash
python -X utf8 scripts/check_orbitcard_openapi.py --config /path/to/private-orbitcard-check.json
```

若只需按 `getProductCode` 示例核实产品价格字段，可加 `--products-only`；此模式只发送一次签名的只读产品查询，不调用其他接口。

脚本检查账户余额、开卡产品、订阅套餐与目录、各已启用套餐的支付地区、分页卡列表、批量与单卡详情、脱敏交易与卡流水、订阅列表，以及配置了编号时的原订阅详情。`getProductCode` 摘要通过 `price_field_present` 和 `plan_ids_with_price` 标明价格字段是否存在及对应套餐，不输出推荐价金额；`id` 中的 `plus`、`pro`、`pro_20x`、`pro_max` 分别对应 Plus、Pro 100、Pro 200、Pro 500。若实际响应缺少对应价格，自动充值会在付款前停止。`max_cards` 默认 20、最多 1000；仅输出字段白名单摘要，不输出 API 凭据、完整卡号、CVV、Session 或原始响应。脚本只允许读取接口，不会开卡、补款或提交订阅。退出码 0 表示已执行的检查成功，2 表示有接口或字段失败，3 表示配置错误；没有卡或未填订单编号时对应检查会标为 `skipped`。真实平台读取仍需要相应 Scope 和允许的服务器出口 IP。

## 支付链路调试

在后台「Orbitcard 配置」下方完成二级验证后，点击「读取可选套餐」，选择 Plus 或三档 Pro；地区沿用该套餐已保存的默认地区。上传或粘贴 Session 后可单独检查 Session、余额、地区和选卡，也可运行完整只读预检。预检实时读取卡片状态、使用次数、占用与余额，展示选卡/补款/开卡/等待的判断和原因；不预占卡、不改卡片记录、不创建订单或执行资金操作。预检通过仅代表当前快照通过，正式支付会再次验证，开卡及补款实际费用以平台为准。

平台没有独立的 Session 上传接口。本地预检只验证 JSON 格式、必要字段和过期时间；只有「真实扣款测试开通」会随 createSubscription 将 Session 发往卡台。该按钮需要确认账号授权及真实扣款，复用管理员 test 订单，不消耗 CDK。测试编号在当前浏览器标签页保留；提交超时后使用原编号查询或继续准备，不自动换编号付款。仅原订单已成功或明确失败后可开始下一笔测试。Session 不写入浏览器存储或日志，受理后清空页面中的 Session。

「全链路持久化日志」显示本地 Session 校验、套餐、地区、选卡与排除原因、开卡/补款、提交及查询结果。预检开始时生成 debug-… 编号，可在执行过程中跟踪；真实测试使用 manual-… 编号。订单列表也提供「链路日志」入口。页面每 10 秒读取后续记录，每页最多 200 条，页面保留最近 1000 条；完整日志可下载。服务重启或清空显示缓存不会删除磁盘记录。API 路径、HTTP 状态、平台代码、耗时及安全参数摘要可查看；Session 内容、访问凭据、完整卡号与 CVV 不记录。
