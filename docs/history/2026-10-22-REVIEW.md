# 2026-10-22 代码整理与支付复核（历史记录）

本轮按生产入口与实际调用关系删除了 `gpt-api-client.js` 转发层、未调用的 API Key 遮罩函数、两个旧配置写入函数，以及支付 worker 的空回调。历史数据迁移和旧套餐别名仍用于读取存量订单，继续保留。

已修复并添加回归场景：

- **重试订单恢复时提前释放卡片**：第二、三次支付尝试在 `prepared` 阶段中断时，先核对原开卡和补款意图，再决定转人工。资金结果未知时转为 `card_pending` / `funding_pending` 并保留卡片；售后锁定事务也重新检查待确认资金记录，防止旧快照释放卡片。
- **余额恢复串用 API 账号**：余额锁定任务含原 API Key 指纹时，恢复前验证当前指纹，避免用另一账号的余额解除原 CDK 锁定。
- **前台重试入口被隐藏**：查询返回 `retry` 后显示 Session 表单，允许继续原账号的支付尝试；查询失败或网络异常时清除旧验证码入口。
- **限流等待时间丢失**：分别解析各层重试提示，忽略无效值，并取有效值中的最长等待时间；异常正文不再使有效 `Retry-After` 失效。
- **重复对账查询**：订阅后的只读对账从四次平台请求减至三次，卡片详情只读取一次；账户、卡片与交易查询仍独立保留成功证据。

以下结果仅记录 2026-10-22 版本：验证使用模拟数据库、平台及前端 DOM，不发起真实开卡、充值或订阅；当时 `npm test` 为 195 项通过（原 189 项，新增 6 项），该次发布未新增环境变量、依赖或数据库字段。后续版本的管理员换卡历史需要 `orbitcard_admin_orders.retry_history` 启动迁移，测试数量以本次运行结果为准。

尚需部署环境验证的边界：真实 MySQL 的多连接竞争和断连恢复，以及真实平台的失败、限流与流水返回。当前接单容量由进程内集合控制，多实例部署时不是全局容量上限；选卡与资金提交仍由分配锁串行协调，补款两次只读核对之间释放全局分配锁。多实例吞吐仍受平台限流、数据库执行锁容量和正在等待的任务数量约束。
