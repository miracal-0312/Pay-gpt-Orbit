# 订单人工处理

后台所有订单行均提供「人工修改」入口，包括准备中、排队、暂停、关闭、失败、成功和历史订单。自助兑换订单在「订单与概览」，管理员测试与人工交付订单在「调试与日志 → 订单链路」。入口不按暂停原因、订单来源或当前结果隐藏。人工成功或失败一经保存，业务订单即关闭，无论原资金是否仍待核对；备注和暂停不关闭业务订单。

## 使用方法

1. 管理员登录后完成二级验证，点击对应订单的「人工修改」。读取订单处理信息和历史记录同样需要二级验证。
2. 弹窗首先显示业务订单是否关闭和已登记的人工结果，原状态与资金结算提示收纳在折叠的「原资金核对记录」中。选择措施，填写 1–255 字的处理原因；登记人工结果时写明核对依据和实际交付情况。
3. 登记成功或失败时，可按实际需要勾选「同时释放原订单本地占用」。默认不勾选；备注和暂停不能选择。释放仅解除本地占用，不会退款或撤销卡台请求，原扣款仍可能完成。原记录继续保留核对；仍须填写处理原因，无需额外确认弹窗。
4. 保存成功后，对应列表自动刷新。若提示「处理已保存，但列表刷新失败」，重新加载列表即可，已经保存的操作不需要重做。

读取失败时弹窗保留，可点击「重新读取订单状态」。保存失败会保留选择和原因；订单版本冲突时必须重新读取再处理。页面阻止重复保存，服务端仍会重新校验执行锁、订单归属和资金记录，可执行提示不替代提交时的校验。

## 四种措施

| 措施 | 作用与边界 |
| --- | --- |
| 添加处理备注（`note`） | 为任何存在的订单追加跟进记录，不改变付款状态或释放占用。历史、非最新、已关闭或归属待核对的订单仍可添加备注。 |
| 暂停自动处理（`pause`） | 在执行锁和归属校验允许时，停止该订单后续自动支付，保留需要核对的原记录和占用。已结束的订单不再重复暂停。 |
| 人工交付完成（`success`） | 管理员核实已经完成人工交付后登记业务成功并关闭业务订单；有关联 CDK 时按人工核销处理。原资金未决仍可登记结果，选择释放本地占用后，CDK 仍保持已核销，原资金记录继续核对。 |
| 人工确认失败（`failed`） | 登记人工失败结果并关闭业务订单、停止自动支付；默认保留 CDK 售后锁定。只有明确勾选本地释放且归属校验通过，才释放未核销 CDK；已经核销的 CDK 不撤销核销，已确认成功的订单不能改成失败。 |

登记人工结果仍需执行锁和订单归属校验；不可执行的措施会在弹窗中说明原因。可执行的措施也可能附带「原资金仍需核对」等提示，这不表示禁止登记人工结果。历史状态无法安全转换、订单已关联后续任务或占用归属不一致时，先追加备注，不能越过保护修改其他任务的结果。

## 资金与平台结果

人工交付结果与原资金结算分开保存。例如订单为 `manual / funding_pending`，管理员已使用另一张卡完成交付，可选择「人工交付完成」并记录原因。列表主状态显示「已关闭（人工成功）」，原补款待核对状态保存在折叠的「原资金核对记录」中，不再显示为业务订单继续处理中；不能因为客户已收到交付就认定原补款结束。若同时选择本地释放，列表另显示「本地占用：已释放」。

有未决开卡、补款、已提交但结果未知的订阅，或缺失、冲突的资金归属记录时，资金结算提示会说明还需核对。未决资金本身不阻止登记人工成功／失败；记录结果后继续按原身份核对原资金。未勾选本地释放时，未决占用继续保留，已完成核对的占用按正常结案规则处理；人工失败的未核销 CDK 仍保留售后锁定。

明确勾选本地释放时，服务端单独核对原订单与实际占用归属，只解除允许解除的本地占用，不把未知资金改成成功或失败，不退款、不撤销平台请求。卡片或 CDK 已由其他任务占用时不能误释放，弹窗会禁用选项并显示原因；已释放时显示管理员、时间和原因。人工处理接口不会创建、重发开卡、补款或订阅请求，也不会提供恢复付款操作。

暂停不会撤销已经发送到平台的请求，平台仍可能完成原操作。原资金仍须按既有恢复流程核对：补款只读查询；开卡在已有原平台订单号时，可能沿用已保存的原正文与原幂等键调用 `createCard` 确认原申请，不能更换身份或参数重新开卡。执行中的支付、排队或查单持有执行锁时，状态修改会被拒绝，待原操作结束后再处理；添加备注仍可使用。

人工 `success` 只表示业务上的人工交付完成，不构造平台成功回执，不改写原平台快照，不增加卡片成功订单次数，也不因这一人工标记发送「充值成功」邮件。卡片成功次数和充值成功邮件仍要求可验证且归属一致的平台证据；概览按人工结果归入成功或失败，排除在「处理中／待确认」之外；列表保留原资金记录的核对入口，不再提供继续准备、重试或验证码处理入口。有关联 CDK 的人工交付按[商城核销通知](../integrations/CDK-REDEMPTION.md)规则处理，与充值成功邮件是两条独立链路。

「人工修改」提供备注、暂停和登记人工结果。保存后不会自动恢复支付，也不会重新使用已停止订单的 Session。需要后续处理时，先核对原订单和现有占用，再按系统允许的流程操作。

## 审计与并发修改

每次成功处理都会向 `order_manual_actions` 追加一条记录，保存订单类型与标识、措施、原因、管理员、时间、修改前后的状态及是否选择本地释放。已有记录不被覆盖；更正说明应追加新备注。订单变更、本地释放和审计在同一事务中提交，失败时整体回滚。弹窗提供最近处理记录，不返回 Session、支付凭据或完整原始资金响应。

读取接口返回不透明的 `revision`，页面保存时原样提交为 `expected_revision`。订单内容、人工处理记录、资金证据或关联占用变化后，旧版本提交返回冲突，防止管理员基于过期信息处理。重新读取保留尚未提交的原因，但应结合新状态重新核对措施。

启动迁移会建立审计表，并为 `task_logs`、`orbitcard_admin_orders` 补充人工结果及本地释放字段，为 `orbitcard_card_fundings`、`orbitcard_card_issues` 补充本地释放记录，为 `order_manual_actions` 补充 `release_local_hold` 审计选项。既有安装的数据库账号需要 `ALTER` 权限；旧数据不会因升级自动释放占用。本次业务闭单展示直接由已有 `manual_result` 派生，不新增迁移字段；旧人工成功／失败记录无需再次保存即可显示已关闭。更新和数据库备份步骤见[部署与升级](DEPLOY.md)。此功能不改变「CDK 管理」中独立的出库与人工核销规则，见[使用与后台管理](USER-GUIDE.md#编辑库存与核销状态)。

## 管理接口

接口同时要求管理员登录令牌 `Authorization: Bearer …` 和有效二级令牌 `x-admin-secondary-token`。处理接口使用 `Cache-Control: no-store`；不要把令牌放在 URL 中。

| 对象 | 读取当前状态与措施 | 提交人工处理 |
| --- | --- | --- |
| 自助兑换任务 | `GET /api/admin/orders/:jobKey/manual` | `POST /api/admin/orders/:jobKey/manual` |
| 管理员测试／人工交付 | `GET /api/admin/manual/orders/:requestId/manual` | `POST /api/admin/manual/orders/:requestId/manual` |

GET 成功响应为 `{ "success": true, "data": { ... } }`。`data` 包含：

| 字段 | 含义 |
| --- | --- |
| `kind`、`id` | `task` 或 `admin`，以及原订单标识 |
| `status`、`state` | 当前原单与资金处理状态，不代表业务订单仍在处理中 |
| `business_status`、`business_result`、`business_closed_at` | 人工终态时分别为 `closed`、`success`／`failed` 及人工结果登记时间；无人工终态时沿用原业务状态 |
| `manual_result` | 已登记的人工结果：`success`、`failed` 或 `null`；独立于原资金是否结束 |
| `manual_result_reason`、`manual_result_by`、`manual_result_at` | 人工结果的原因、管理员及登记时间 |
| `settlement` | `{ allowed, reason }`，表示当前是否满足安全结算条件及原因；`allowed: false` 不等于禁止登记人工结果 |
| `release` | `{ allowed, reason, released }`，表示是否可明确解除本地占用、不可执行原因及是否已释放；须同时选择 `success` 或 `failed` 才可提交释放 |
| `manual_local_released_at`、`manual_local_released_by`、`manual_local_release_reason` | 已执行本地释放的时间、管理员及原因 |
| `revision` | 保存时必须原样提交的版本，不自行计算或复用旧值 |
| `actions` | `{ value, label, enabled, reason }` 数组；以 `enabled` 判断当前措施是否可提交，`reason` 也可为可执行措施提供资金待核对提示 |
| `history` | 最近人工记录，含 `action`、`reason`、`admin_email`、`created_at`、`previous_status`、`next_status`、`release_local_hold` |

POST 请求体示例，`expected_revision` 必须替换成刚读取的 `data.revision`：

```json
{
  "action": "note",
  "expected_revision": "<从 GET data.revision 原样取得>",
  "reason": "已核对原补款，等待平台更新最终结果",
  "release_local_hold": false
}
```

`release_local_hold` 必须为布尔值，不接受字符串 `"true"`／`"false"`；仅 `success`／`failed` 可以传 `true`，并须通过最新的占用归属校验。它不表示平台退款或原资金已完成结算。POST 成功返回 `{ "success": true, "data": { ... }, "message": "..." }`，`data` 为处理后的同类视图。读取和提交的主要错误如下：

| HTTP 状态 | 处理方式 |
| --- | --- |
| `400` | 修正订单标识、措施、原因或版本参数。 |
| `401`／`403` | 重新登录或完成二级验证后，再读取原订单。 |
| `404` | 核对订单标识，原记录不存在。 |
| `409` | 订单或资金证据已变化、执行锁忙、归属不符或措施不允许；按返回原因核对并重新读取，不绕过保护。 |
| `503` | 服务暂不可用；查询原订单及处理记录后再决定是否重试，不能据此假定操作未保存。 |

旧 `POST /api/admin/orders/:jobKey/status` 仅保留兼容，成功／失败修改转入同一人工处理服务，仍检查旧调用的 `expected_status` 并应用统一执行锁、归属、资金和审计保护。新页面使用上述 `/manual` 接口，旧入口不能绕过这些校验。
