# 运行、资源与数据保留

API 在解析请求体、认证和访问数据库前限流。默认每个 IP 每分钟补充 180 个请求额度，其中写操作最多 30 个；公共卡密验证和查单使用普通请求额度。全进程每分钟补充 1200 个请求额度，允许对应额度的短时突发。全进程最多同时处理 64 个 API 请求，同一 IP 最多 12 个。超额返回 `429` 或 `503`，附带 `Retry-After` 与 `retry_after_ms`，调用方应等待后再查询；支付提交超时后应先查原单，不能直接重发支付。

这些上限可通过 `.env.example` 中的 `API_*` 调整，设置为 0 或非法值不会关闭保护。HTTP 连接默认最多 500；WebSocket 默认最多 200 个连接、每个 IP 最多 5 个。WebSocket 订阅串行处理，每连接每分钟最多补充 30 条消息及 6 次订阅额度，未订阅、心跳失联或发送缓冲堆积的连接会关闭。限流状态保存在各进程内；多实例部署需要在反向代理统一限制总量。

直接访问时 `TRUST_PROXY` 留空。通过 Nginx 等代理访问时，只填写实际代理 IP/CIDR（本机代理可填 `loopback`）；HTTP、登录验证和 WebSocket 共用这一信任规则。未配置可信代理时按连接来源 IP 计数，代理后的用户会共享额度。不要把任意客户端或整个公网设为可信代理。

数据库查询连接默认 20 个、排队最多 100 个、支付执行锁专用连接最多 32 个，分别由 `DB_POOL_LIMIT`、`DB_QUEUE_LIMIT`、`DB_LOCK_LIMIT` 控制；满额时拒绝新增工作，不驱逐正在支付的执行锁。Orbitcard 最多 32 个并发请求，Telegram 最多 8 个，均有响应大小限制和绝对超时。查询及认证缓存有容量与过期清理，原订单故障查单从 30 秒逐步退避至最多 5 分钟；未确认订单仍保留身份等待后续核对。商城通知保持每个事件最多发送 3 次。

浏览器隐藏页面时暂停自动查询；订单与后台自动跟踪最多持续 15 分钟（不缩短服务器的 30 分钟共享等待），后台连续失败 5 次后暂停，可手动刷新或重新勾选跟踪恢复。后台相同在途请求合并，最多同时发出 8 个通用 API 请求，单次最多等待 120 秒。上述保护无需新增数据库字段，重启服务、刷新页面后生效。

## 内存与数据库连接

运行内存：日志预览采用序列化环形缓存，默认最多 2000 条、4 MiB 字符串预算（按每字符 2 字节计，另有少量索引开销），由 `LOG_CACHE_ENTRIES`、`LOG_CACHE_BYTES` 调整。超大单条仅缩短内存预览，完整脱敏审计日志仍写磁盘供下载；启动时最多读取最近 1 MiB 日志恢复预览。日志翻页按记录读取，避免先拆分整页文本。浏览器链路日志也限制总字符数与单条预览长度。

数据库查询池默认最多保留 5 个空闲连接，60 秒后回收多余空闲连接，每个连接最多缓存 256 条预处理语句；可通过 `DB_MAX_IDLE`、`DB_STATEMENT_CACHE_LIMIT` 调整，支付执行锁连接不受空闲回收影响。订单查询缓存每 30 秒清理到期数据，在没有新请求时也会释放结果。上述设置约束各缓存与连接的资源占用，并非整个 Node.js 进程的内存硬上限。

## 日志与持久数据

任务、CDK 和订单绑定保存在 MySQL；运行与任务 JSONL 日志默认保存在系统盘：Linux 为 `/var/log/pay-gpt-orbit`，Windows 为系统盘的 `ProgramData\Pay-gpt-Orbit\logs`，后台可下载。日志按北京时间分天保存，保留当天及之前 14 天，共 15 个自然日；每天零点直接删除过期日期的日志，不每小时检查，也不逐条读取或重写。启动时只补清理停机期间过期的日志，随后定时器等待下一个零点。运行日志按文件名日期分组，订单日志存入日期目录，支持跨天查看与合并下载。旧版未分天的订单日志按文件修改日期整份清理。完整 Session、签名和验证码凭据不写入任务数据库或普通日志。验证码链接仅保留在响应和短时内存中。

升级保留旧数据库表、历史账单和 Session 数据；磁盘日志按上述 15 天策略清理。历史非 Orbitcard 运行任务转为人工核对并保留 CDK；这些数据不会被重新执行，也不再提供原有支付入口。

日志路径、卷挂载、权限与迁移步骤见[部署说明](DEPLOY.md#环境更新与存储)。共享等待规则见[使用说明](USER-GUIDE.md#等待与接单)。
