# 使用与后台管理

管理员邮件提醒位于「接单与安全」，需要二级验证。可分别开启账户低余额、充值成功和充值失败提醒，配置 SMTP 与管理员邮箱，并发送测试邮件。默认关闭；使用方式见[管理员邮件通知](EMAIL-NOTIFICATIONS.md)。

## 首次业务配置

先按[部署说明](DEPLOY.md)配置数据库、管理员及配对的 `ORBITCARD_API_KEY` / `ORBITCARD_API_SECRET`。卡台凭据只从服务端环境变量读取，后台仅显示配置状态，不接收、回显或保存密钥。

1. 在「Orbitcard 配置」保存 HTTPS 根域名，再从平台刷新套餐、地区、渠道和 BIN。
2. 为 Plus、Pro 100、Pro 200、Pro 500 分别填写对应地区的「套餐卡支付金额（USD）」。配置保存在 `orbitcard_plan_prices`，最多 8 位小数；留空暂停对应套餐。产品接口不提供套餐报价，USDT 服务费不能代替卡支付金额。
3. 各档默认地区来自 `getSubscriptionPaymentRegions`。「平台默认」不发送 `payment_region`；指定地区在资金操作前校验。地区修改或平台价格变化后，重新核对 USD 金额。自助和管理员共用此配置。
4. 按需多选开卡渠道（`product_code`）及 BIN，两个选项组各自留空表示全部，同时选择取交集。渠道、BIN 和开卡产品规则只用于手动开卡、错误补开与满额补开，不筛选现有支付卡。设定单卡首充上限及最高 USDT 服务费；首充上限仅影响开卡，服务费上限仍用于订阅下单。开卡首充固定 20 USD，数量 1，后台不接受自定义开卡金额。
5. 在「调试与日志」完成接口查询和只读预检，确认权限、余额与可用卡后开放接单。手动开卡直接进入共享卡池；错误补开和人工恢复详见[卡片规则](ORBITCARD-CARDS.md)。

新补款按本次套餐完整 USD 金额执行。例如套餐 20 USD、卡余额 5 USD，需补款时充值 20 USD；卡内余额足够覆盖套餐 USD 金额时不补款，不叠加开卡产品最低留存。账户余额不足会提示联系客服。升级前原资金意图仍按原金额、已保存的目标余额（`target_balance`）、正文和幂等键核对，不能按新规则改写或重充。

CDK 管理实时读取 `getSubscriptionPlans`，生成/导入时再次确认套餐开放。新 CDK 为「自助」类型，格式 `YZW-{12位随机字符}-{短套餐代码}`；套餐以数据库 `plan_type` 为准。人工交付使用同一批自助 CDK，历史手动 CDK 仍保留。

## 界面与导航

用户兑换页按「验证卡密 → 提交 Session → 查询结果」显示当前步骤。后台采用侧栏导航，手机上通过左上角菜单切换页面；地址栏仅保留当前功能页标识，刷新后可返回同一页。

前台粘贴有效 Session 后，会弹窗展示账号邮箱和充值套餐，要求确认是否为目标账号；确认账号后再点击「确认充值」。直接点击充值但尚未确认账号时，也会先弹窗确认。取消或按 Esc 不提交订单，更换 Session 或重新验证卡密后需再次确认。弹窗只在浏览器中读取 Session，不额外请求卡台；账号确认状态仅保留在当前页面内存中。

充值成功弹窗展示原订单的目标邮箱和充值套餐。信息由原订单查询返回，刷新页面后输入原卡密查询也可显示，无需重新提交 Session；历史记录缺少字段时明确显示未记录，不使用当前输入的其他账号补充。

兑换页手动查询后继续自动跟踪；每次请求最多等待 30 秒，提交超时或返回结果不明时保持待确认并查询原订单，不自动重发充值。订阅未提交且占用已安全释放，或平台明确拒绝提交时显示「重新验证并继续充值」，重新校验卡密后才开放提交。已验证订阅明确出现卡片错误时，最多换两张不同卡继续尝试，总计最多 3 次；原 Session 不可用时保留剩余额度，要求原账号的新 Session。无可等待的合格现有卡、等待失败、重试准备失败或次数耗尽时保留 CDK 供售后处理。查询遵守服务端等待间隔。「卡片与开卡」展示成功会员订单次数；实际支付预选无合格现有卡时按需补开，后台提供人工停用与恢复入口。

后台统一使用「调试与日志」入口，包含「接口查询」「支付预检与测试」「订单链路」「运行日志」「登录记录」五个子页。当前注册的 13 项卡台接口统一由「接口查询」的「一键全部测试」检查；Telegram 发送测试也位于该子页的独立通知测试面板，使用已保存的通知配置真实发送消息，设置页保留快捷入口；只读预检、并发选卡模拟及真实扣款测试位于「支付预检与测试」。管理员订单列表与任务链路日志统一在「订单链路」，订单列表保留日志快捷入口；「手动开通」仅用于人工交付，并链接到订单记录。旧 `#logs` 地址自动进入「运行日志」。默认充值地区及接单开关仍在配置页设置。订单、CDK、管理员订单和卡片列表支持搜索当前已加载的数据；搜索不会改变 CSV 导出范围，导出使用 CDK 列表上方的套餐、使用状态、出库状态和导出配置。日志支持复制和自动换行切换。

手动申请卡片直接加入共享卡池，无需选择关联套餐；提交 `POST /api/admin/orbitcard/cards/apply`，Body 为 `{}`。旧申请仍通过“确认原开卡 / 补款”沿用原参数和幂等键恢复。产品查询只展示产品信息及统一开卡参数，不再附带每产品的套餐映射。管理 HTTP 请求统一使用 `Authorization: Bearer`，不再接受 URL 中的 `token`；套餐余额状态查询不再附带 `recent_orders`，原订单列表和查单功能保留。

浏览器截图和模拟测试工具不包含在生产镜像中。

## 等待与接单

用户兑换、管理员真实测试和人工交付共用一个等待位。当支付并发名额已满，或符合其他条件的现有卡暂被占用时，最多受理 **1 个等待任务**；等待位也满时弹窗提示 **10 分钟后再下单**。已等待的原 CDK、管理员 `request_id` 和本次支付身份保持不变，无需重复提交。等待本身不触发开卡；已登记的卡片错误补开可在同一等待位确认。不同订单不会同时占用同一张卡；卡库存为空、卡片停用或资料异常仍按原准备失败规则处理。

等待最多 **30 分钟**。上一任务释放卡片后，本地停用标记、平台状态、余额及未决资金校验全部满足时，等待任务在下一轮检查后自动继续；自动流程不会因前单结果未知而释放或复用其卡片。管理员通过[订单人工处理](ORDER-MANUAL-CONTROL.md)明确解除本地占用属于单独授权的例外，后续选卡仍需通过实时可用性检查，原资金继续核对。没有额外的固定卡片冷却等待。等待沿用 `preparing` 状态，并显示原因。`/api/public/runtime` 的 `active_foreground_jobs` 不计等待任务，另返回 `waiting_jobs` 和固定为 1 的 `max_waiting_jobs`。

等待中的 Session 仅存在当前工作流内存中，按自身 `expires` 和 30 分钟等待截止校验，不使用管理员失败续试的 15 分钟缓存期限。Session 到期、停机或等待超时后，首笔尚未付款且无未决资金的订单安全释放，用户需重新验证并提交新 Session；已有支付失败记录的重试 CDK 保持售后锁定。进程重启沿用现有 `preparing` 恢复规则，不持久化 Session 或自动恢复丢失的等待工作流。固定 MySQL 命名锁保证共享等待位唯一，此功能不新增数据库字段或环境变量；同一套任务仍只部署一个应用实例。

## 管理员上传 Session 开通

后台「手动开通」仅用于人工交付；真实测试统一在「调试与日志 → 支付预检与测试」，两者均需管理员登录和二级验证。套餐从 `getSubscriptionPlans` 实时读取，仅显示当前 API Key 开放的 Plus 和三档 Pro。上传或粘贴完整 Session 并选择套餐后，提交时实时读取账户、卡列表及批量详情，只选无本地停用标记、ACTIVE、USD、未占用的现有卡；换卡排除此前尝试过的卡，优先使用现有健康卡，不因开卡渠道或产品库存不可用而阻断。现有卡支付准备不查询开卡产品目录。卡内足额直接准备订阅；不足时检查账户余额并按所选套餐全额补款一次，首笔账户不足提示联系客服，并释放无未决资金操作的占用。候选卡仅因占用不可用时申请共享等待位。实际支付预选无合格现有卡时按需补开。关闭公共接单时已授权的管理员仍可使用现有卡。整批详情缺失或原资金未知保留原请求待确认。

- **测试开通**：真实调用 `createSubscription` 并从自动选中的卡扣款，不需要或占用 CDK。即使前台新订单开关关闭，已配置凭据的管理员仍可测试。
- **人工交付**：输入匹配套餐的未使用自助 CDK。提交前事务占用 CDK 和支付卡，平台确认成功后核销 CDK。已验证的卡片相关失败最多换两张不同卡，期间保留 CDK，每张失败卡释放；无可等待的合格现有卡、等待失败、重试准备失败或耗尽后进入 `support_locked`。首笔可信的非卡片创建拒绝进入 `rejected`，无未决资金才释放 CDK；可信 `59005` 按卡片错误和剩余额度处理。

两种模式都先保存唯一管理员订单，每次尝试资金就绪后，用该次固定 `client_order_no` 原子认领并提交一次。确认卡片相关失败且仍有额度，才生成下一次尝试身份，旧失败结果追加到 `retry_history`，业务 `request_id` 不变；总计最多 3 次，始终排除用过的卡。管理员 Session 仅在内存保留最多 15 分钟、64 份；失效或重启后保留 `retry_waiting`，用原 `request_id` 与同账号的新 Session 继续剩余额度。订阅超时或未知保持 `pending`，只查原单。资金异常不会触发换卡：有原补款号时每至少 5 秒只读核对，更长 `Retry-After` 优先，原 Session 等待最多 120 秒；窗口内足额且 Session 有效才继续同一订阅。超时、失效或重启后转 `funding_review`，确认原资金 `ready` 或 `failed` 后安全收尾，首笔普通交付需最新 Session 和新请求编号，支付重试中的 CDK 保持售后锁定。历史 `funding_pending`、`card_pending` 按原身份核对，不恢复会员付款；未知资金不得换身份重放，历史 `manual` 保留人工语义。管理员订单状态、验证码链接和持久化日志统一在「调试与日志 → 订单链路」，Session 不写数据库、浏览器存储或日志。第 2、3 次尚在准备阶段的管理员订单恢复时，沿用当前尝试身份，不重置或额外消耗次数。

管理员订单在 `preparing`、`prepared`、`funding_waiting`、`funding_review`、`funding_pending`、`card_pending` 阶段不调用 `getSubscription`。提交后查询校验原平台与 API Key 身份，并按至少 5 秒及平台 `Retry-After` 间隔合并刷新请求。自助订单同样校验已保存的 API Key 身份；切换平台账号后不能用新凭据查询原订单。

## 人工处理所有订单

「订单与概览」中的自助订单，以及「调试与日志 → 订单链路」中的管理员测试、人工交付订单，每行均提供「人工修改」。准备中、排队、暂停、关闭、失败、成功和历史订单都保留入口，不按停止原因隐藏。

完成二级验证后，打开弹窗读取当前状态，可选择「添加处理备注」「暂停自动处理」「人工交付完成」「人工确认失败」，并填写处理原因。不能执行的措施会显示原因；历史或非最新订单仍可追加备注。暂停及登记人工结果需要服务端执行锁与归属校验。原开卡、补款或订阅未决时，仍可登记已通过其他卡完成的人工交付或人工失败结果，业务订单立即关闭，原资金核对状态独立保留，也不会自动恢复付款。备注和暂停不关闭业务订单。

登记成功或失败时，可勾选「同时释放原订单本地占用」，默认不勾选。未勾选时，未决占用继续保留，已完成核对的占用按正常结案规则处理。明确释放只解除本地占用，不退款、不撤销卡台请求，原扣款仍可能完成，原资金记录继续保留核对。成功 CDK 仍保持已核销；人工失败且明确选择释放时，才释放未核销的 CDK。错归属会禁用释放并说明原因，列表与弹窗显示已释放标记。

订单列表主状态显示「已关闭（人工成功／人工失败）」，原状态及资金消息折叠在「原资金核对记录」中，弹窗同样先显示业务已关闭。概览按人工结果计入成功或失败，不再计入处理中／待确认；旧人工结果直接生效，无需再次保存。人工交付完成仅登记业务人工结果，不生成平台成功凭证，不增加卡片成功次数，也不因此发送充值成功邮件。例如 `manual / funding_pending` 订单登记人工交付完成后，业务已关闭，只保留原补款的只读核对入口。人工失败未释放的 CDK 仍为占用中，显示「订单已关闭；CDK保留售后占用」，不表示订单仍待确认。所有处理追加审计记录；状态变化时拒绝过期保存，要求重新读取，保留尚未提交的输入。详细操作、资金保护和接口见[订单人工处理](ORDER-MANUAL-CONTROL.md)。

## 状态与数据

任务、CDK 和订单绑定保存在 MySQL；运行与任务 JSONL 日志默认保存在系统盘：Linux 为 `/var/log/pay-gpt-orbit`，Windows 为系统盘的 `ProgramData\Pay-gpt-Orbit\logs`，后台可下载。日志按北京时间分天保存，保留当天及之前 14 天，共 15 个自然日；每天零点直接删除过期日期的日志，不每小时检查，也不逐条读取或重写。启动时只补清理停机期间过期的日志，随后定时器等待下一个零点。运行日志按文件名日期分组，订单日志存入日期目录，支持跨天查看与合并下载。旧版未分天的订单日志按文件修改日期整份清理。完整 Session、签名和验证码凭据不写入任务数据库或普通日志。验证码链接仅保留在响应和短时内存中。

升级保留旧数据库表、历史账单和 Session 数据；磁盘日志按上述 15 天策略清理。历史非 Orbitcard 运行任务转为人工核对并保留 CDK；这些数据不会被重新执行，也不再提供原有支付入口。

### 按配置导出卡密到商城

「CDK 管理 → 卡密列表」统一配置并导出已保存的卡密，不再提供仅保留本次生成批次的下载入口。选择套餐、使用状态和出库状态（默认未使用、未出库），列表与导出共用这些条件。导出数量可留空导出全部，或填写 1–100000，按最新创建顺序选取，匹配不足时导出全部匹配卡密；导出不受列表 2000 条上限影响，列表文本搜索不参与导出筛选。

导出格式默认「商城导入 CSV」，文件为 UTF-8 BOM CSV，表头 `secret`、每行一个卡密，可在 dujiao-next 的「CSV 导入」页面导入。也可选择「管理明细 CSV」，包含卡密、套餐、状态、出库、创建时间。默认勾选「导出后标记为已出库」，仅标记实际导出的卡密；取消勾选则保留出库状态。没有匹配卡密时不下载文件、不修改出库状态。刷新页面后仍可从列表重新筛选已保存的卡密。

管理接口 `POST /api/admin/cdks/export` 接受查询参数 `plan_type`、`status`（`unused` / `processing` / `redeemed`，留空为全部）、`shipped`（`true` / `false`，留空为全部）、`quantity`、`format`（`secret` / `detail`）、`mark_shipped`（`true` / `false`）。为兼容旧调用，省略参数时仍导出全部匹配套餐的管理明细并标记出库；页面会显式发送所选配置。接口沿用管理员登录与二级验证。

### 编辑库存与核销状态

转人工处理后，任务会退出自动支付。每次补款和订阅提交前都会重新检查订单状态。后台核对原资金流水时取得原订单执行锁并重新检查。管理员可主动按原身份确认符合条件的开卡申请。人工核销停止后续支付，但不会中断已提交资金的核对；结果确认后可释放卡片，已核销 CDK 始终保持核销。普通 `manual` 任务不会重新进入自动付款。原记录保留供售后处理，此人工处理策略复用原状态字段；管理员换卡历史另由启动迁移补齐 retry_history；已经发给平台的请求仍可能由平台完成，本系统不自动撤销或另建资金请求。

后台「CDK 管理」完成二级验证后，每条卡密均提供「修改状态」按钮。点击打开编辑窗口，直接选择使用状态、出库状态并填写修改备注，点击「保存状态」生效。出库状态可在「未出库／已出库」之间切换；未使用或占用中的卡密可人工标记为「已核销」，已核销卡密不能改回未使用。支持单独修改出库状态，也可与核销一起保存。保存后自动刷新列表；若原状态已被其他操作改变，接口会拒绝过期修改并提示刷新。

核销前须配置[商城核销通知](../integrations/CDK-REDEMPTION.md)的地址、来源和密钥；仅修改出库状态无需配置通知，也不会发送核销凭证。人工核销、出库变更、商城通知入队及操作记录在同一数据库事务中完成，任一写入失败则整体回滚。状态变更记录管理员、原状态、目标状态和备注，可在「调试与日志 → 登录记录」查看 `cdk_status_changed` 记录。后台发送器通常在下一次 5 秒轮询发送，失败自动重试，每个通知最多发送 3 次（含首次发送，即最多再重试 2 次）；页面显示「通知已入队」表示已持久保存，并不表示商城已接收。重复提交不覆盖首次核销备注，也不产生新凭证。

系统记录人工核销时间、管理员邮箱与售后备注，列表会显示这些信息；列表、CSV 和 `/api/cdk/status` 均返回已核销。原平台订单与支付卡计数继续按实际支付结果核对，原订单失败不会释放已人工核销的卡密，也不会为它创建或继续支付重试。支付或查单持有执行锁时须稍后再修改；仍处于准备阶段的管理员人工交付订单须先通过[订单人工处理](ORDER-MANUAL-CONTROL.md)核对并处理原订单。该限制属于 CDK 独立核销操作，不影响在订单中追加处理备注。

升级启动时自动为 `cdk_codes` 补充 `manual_redeemed_at`、`manual_redeemed_by`、`manual_redemption_reason` 三个字段。管理接口为 `POST /api/admin/cdks/:cdk/status`，沿用管理员登录令牌和二级令牌，请求体例如 `{"status":"redeemed","shipped":true,"expected_status":"unused","expected_shipped":false,"reason":"人工交付完成"}`。`status` 只支持目标 `redeemed`，`shipped` 为布尔值，未修改的字段可省略；至少提供一个目标字段。页面发送原使用状态与出库状态用于检测过期编辑。保留兼容仅发送 `status` 和 `reason` 的原核销调用。

### 查询 CDK 是否已核销

`POST /api/cdk/status`，请求头 `Content-Type: application/json`，请求体为 `{"cdk":"你的卡密"}`。持有卡密即可查询，无需管理员登录或提供 Session。

```bash
curl -X POST 'https://你的域名/api/cdk/status' \
  -H 'Content-Type: application/json' \
  -d '{"cdk":"你的卡密"}'
```

已核销时返回 HTTP 200：

```json
{
  "success": true,
  "data": { "status": "redeemed", "redeemed": true },
  "message": "CDK 已核销"
}
```

| `data.status` | `data.redeemed` | 含义 |
| --- | --- | --- |
| `redeemed` | `true` | 已核销，包含平台确认成功、管理员人工核销和人工交付完成；不单独证明平台付款成功 |
| `processing` | `false` | 已占用但尚未确认核销，包括处理中、待确认、重试或售后锁定 |
| `unused` | `false` | 未使用或已释放 |

`success` 表示查询成功，不表示充值成功；请以 `data.redeemed === true` 判断已核销。`redeemed: false` 不代表可以再次兑换，应结合 `status` 判断。

接口只读取本地数据库的已保存状态，与后台 CDK 列表一致，不主动向平台查单，也不会发起充值或改变 CDK 状态。平台刚完成充值时，需等待后台查单同步后才会显示已核销。响应不包含账号、Session 或支付资料，并设置 `Cache-Control: no-store`。

CDK 格式错误返回 HTTP 400，不存在或已停用返回 HTTP 404，服务异常返回 HTTP 503；错误响应为 `{"success":false,"message":"错误说明"}`，不返回 `redeemed: false`，避免将查询失败误判为未核销。

卡片故障分类、59005 拒绝、唯一补开及人工恢复见[卡池规则与故障处置](ORBITCARD-CARDS.md)。Session、账号、配置或未知原因的已确认终态失败进入 `support_locked`，不会自动换卡；受理结果未知只查询原订单。日志与容量配置见[运行与资源](RUNTIME.md)，诊断入口见[调试与验证](DIAGNOSTICS.md)。
