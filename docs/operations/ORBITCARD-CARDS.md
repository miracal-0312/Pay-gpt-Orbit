# Orbitcard 选卡、自动补款与卡池维护

## 卡片可用状态与错误补开

卡片按平台 ACTIVE、USD、实时资料与余额、本地占用、停用标记及未决资金判断可用性。成功会员订单数继续按 `orbitcard_successful_orders` 去重累计，作为统计展示。历史 `orbitcard_max_authorizations` 配置停止参与选卡、事务预占、退役、预检及并发模拟。

自助兑换、管理员测试和人工交付在确认原订阅归属一致且终态失败后，读取 `failureCode` 和 `failureMessage`。明确的卡片拒付、过期、无效、冻结、受限、卡内资金不足及 CVC/CVV 错误会保存 `disabled_at`、`disabled_code`、`disabled_reason`、`disabled_job_key`，并与订单结算及卡片释放在同一事务提交。创建订阅返回 `59005` 时，还须确认无订单身份冲突、上游受理结果等矛盾证据，才能按明确拒绝处理。Session、账号、配置及未知终态失败停止后续支付并进入售后核对，不停卡、不补开；验证码、网络、超时与查询异常只核对原订单。

统一规则位于 `src/orbitcard/orbitcard-error-policy.js`，`src/orbitcard/orbitcard-card-failure.js` 在归属与终态守卫通过后执行持久化停用。卡台文档尚未给出完整的 `failureCode` 枚举，当前识别明确的卡片错误码及明确提到卡片问题的说明。Session/账户错误优先于模糊卡片文案；单独的“insufficient funds”、否定描述和 URL 不作为卡片故障证据。未匹配错误保留原失败详情并停止自动支付，管理员可在核对后人工停用卡片。

选卡及后台恢复会为错误停用的卡创建补开申请。补开按平台 scope、原卡 ID 与失败任务身份唯一，申请正文、产品、平台身份及幂等键持久化。网络异常或结果未知时继续确认原申请；明确失败后保留失败记录供管理员核对。新卡固定首充 20 USD，仍需符合产品最低首充、库存、账户余额和后台首充上限。卡片就绪后按原有支付重试规则继续，最多 3 次支付尝试。

后台「Orbitcard 配置」通过 `getProductCode` 读取开卡产品及 BIN，渠道选项使用 `product_code`。`orbitcard_product_codes` 与 `orbitcard_bins` 均为多选数组，各自留空表示全部，同时选择时取交集。在满足库存和首充要求的候选产品间按产品码轮换。旧单一 `orbitcard_product_code` 会迁移为单项渠道选择，手动开卡和错误补开共用选择规则。

后台「卡片与开卡」为每张卡提供人工停用与恢复使用，需要二级验证和修改原因。操作在分配锁与卡片行锁内进行，仍有订单占用或原退役尚未确认时须先核对原记录。人工停用保存 `disabled_code=manual`；恢复使用清除本地停用标记，后续选卡仍实时核对平台状态与资金。管理员操作记入审计日志。恢复后若再次出现新的卡片错误，按新的失败任务创建一笔补开申请。

平台同步仅更新平台摘要，持久化停用记录继续保留。历史删卡意图仍按原身份确认，订单数和卡片总数均不触发新的删卡。未知订阅及原资金操作保留占用并继续对账。

## 共享等待与卡片复用

支付并发名额已满，或其余条件合格的现有卡被其他订单占用时，用户兑换、管理员真实测试和人工交付共用 **1 个等待位**。固定 MySQL 命名锁保证唯一等待位，已满时弹窗提示 **10 分钟后下单**。等待任务沿用原 CDK、管理员 `request_id` 及本次支付身份，保持 `preparing` 状态并更新等待原因。开卡确认中的错误补开也复用此等待位。

等待最长 **30 分钟**。上一任务释放卡片后，停用标记、状态、余额与未决资金检查均通过，才进入分配锁与事务预占，等待任务会自动继续；前单未知时继续占用，等待订单不能抢卡。缺少库存、未知资料和未决补款仍按原保护处理，不存在额外的固定卡片冷却。

等待 Session 仅在工作流内存中，检查自身到期时间和 30 分钟截止；独立于管理员失败续试的 15 分钟缓存。Session 到期、停机或等待超时，首笔未付款且无未决资金时安全释放；支付重试 CDK 保持售后锁定。重启复用现有 `preparing` 恢复规则，不恢复丢失的 Session。此等待功能不新增数据库列或环境变量，仍要求同一套任务只运行一个应用实例。

## 卡片读取与选卡

getCardList 完整分页读取卡片；cardDetail 以 card_ids 分批读取，每批最多 20 张，reveal_sensitive 始终为 false。兼容批量 items/data 结构并校验内外卡 ID、重复 ID 和逐项成功状态。只保存脱敏尾号、状态、余额等摘要，不获取完整卡号或 CVV。

实际支付刷新卡片状态和余额，读取已保存的停用记录；不在支付主链路等待消费授权接口。预占事务再次检查停用记录、任务占用及换卡排除列表。优先选择足额卡或按套餐整额补款后可满足支付目标的卡；足额直接支付，不足时核对账户可用余额并按所选套餐全额补款一次；未决资金只对账，不重复补款。

每卡同一时间只处理一笔订单。未知订阅保留预占；明确终态结算并释放本次占用。成功次数只作统计；明确卡片错误触发持久化停用和补开，人工停用不触发补开。

任务已有补款或历史任务绑定开卡申请时先核对原申请，资金异常或未知结果不能触发换卡。管理员手动开卡使用独立共享卡池申请。自助任务从 `preparing` 开始，资金就绪后转 `prepared`，原子认领 `submitting` 并提交一次；每次尝试均有固定订单身份。未知订阅或超时保持 `pending`，只查原单。只有原订阅归属一致且明确属于卡片失败（或可信的创建 59005 拒绝）时，才保存失败证据、停用并释放本次卡，保留 CDK，按配置补卡及选卡续试，总计最多 3 次。卡片失败后仍有额度但 Session 本地已过期时保持 `retry_waiting`，用原 CDK 或管理员原 `request_id` 及同账号新 Session 继续；次数与已用卡落库，重启不重置。平台确认的 Session/账号/配置/未知终态失败直接转 `support_locked`，需人工核对原因和原链路，不能靠再次提交 Session 自动解锁。无可等待的合格卡、等待失败、重试准备失败或耗尽同样转 `support_locked`。首笔可信的非卡片创建拒绝以 `rejected` 释放占用，修复后可重新提交；显式人工及历史 `manual` 不恢复会员付款。

自助和管理员订单每次尝试只提交一次补款；原补款有平台订单号、仅处理延迟或余额未同步时，进入 `funding_waiting`，每至少 5 秒只读查询原资金流水与选中卡余额，更长的 `Retry-After` 优先。两次核对之间释放全局选卡锁，保留原卡占用与任务执行权；原 Session 最多等待 120 秒，窗口内确认补款成功、余额足额且 Session 有效后提交同一笔订阅一次。超时、Session 失效或重启后转 `funding_review` 人工对账工单（自助任务 `status=manual`），后台继续只读原资金号。`funding_pending` 有已保存的 `order_no` 时也可只读核对原流水；参数、平台和凭据身份仍须一致，不能更换金额或重新补款。补款成功后仍须核对卡片 ACTIVE、USD 和余额足额，才记为 `ready`。确认原资金 `ready` 或明确 `failed` 后，在事务中复核卡片归属和所有未决准备记录，再释放未提交任务；普通 CDK 解除占用并要求最新 Session，已人工核销或支付重试的 CDK 保持锁定。资源收尾不依赖消费授权同步，资金未知或身份异常不能仅因超时释放。

`card_pending` 仅用于历史开卡准备任务：有原平台订单号时，以原 API Key、正文及幂等键确认同一申请，不新建申请或提交会员充值。`prepared` 意图表示未发送，可确认失败；可能已发送却无 `order_no` 不重放，保留人工核对。原记录确认 `ready` 或 `failed` 且无其他未决资金时，事务释放对应卡片，CDK 按人工核销及支付重试规则处理。普通 `manual` 和 `support_locked` 不恢复支付，历史 `balance_blocked` 保留原恢复逻辑。资金恢复复用原资金表和任务字段；本次管理员换卡重试另由启动迁移添加 `orbitcard_admin_orders.retry_history MEDIUMTEXT`，需 ALTER 权限，无新增环境变量。

后台手动申请同样用于共享卡池，不关联套餐，也不接收自定义产品或金额。已有唯一手动开卡申请时继续确认原申请；存在多笔待确认申请或其他订单绑定的申请时停止新增申请，先通过恢复入口处理。历史按套餐记录的申请继续保留原 key 和 Body，不转换成另一笔申请。

## 套餐整额补款

新资金意图以本次所选套餐的 `orbitcard_plan_prices` USD 金额为补款本金。卡内余额已覆盖“套餐金额＋产品最低留存”时不补款；不足时补本次套餐全额，不能减去卡内余额，也不把最低留存额再加到本金。接口金额向上取到美分，配置仍支持最多 8 位小数。

| 套餐金额 | 当前卡余额 | 最低留存 | 本次行为 |
| --- | --- | --- | --- |
| 20 USD | 5 USD | 0 USD | 补款 20 USD，到账后再校验支付条件 |
| 20 USD | 20 USD | 0 USD | 余额足额，不补款 |
| 20 USD | 1 USD | 2 USD | 补 20 USD 后仍不足 22 USD 目标；不创建补款意图，提示联系客服 |

选卡优先选择足额或整额补款后可满足留存条件的卡。补款前验证平台账户 `available_balance` 是否覆盖本次套餐补款金额；不足时前台提示联系客服，不发送充值请求。首笔尚未付款且无未决资金可安全释放，已有重试或未决资金仍按原锁定/对账规则处理。

每次尝试仍只提交一次补款，确认后再次检查卡片 ACTIVE、USD 和余额足额，不能因余额延迟追加第二笔。升级前已经持久化的开卡/补款意图继续使用原金额、原正文、原幂等键和原平台身份；不按新规则改写或重新充值。

## 后台与数据库

在「Orbitcard 配置 → 套餐卡支付金额（USD）」分别填写 Plus、Pro 100、Pro 200、Pro 500 金额。配置键 orbitcard_plan_prices 使用套餐到十进制定点字符串的 JSON 对象，最多 8 位小数，禁止非正数、指数格式和未知套餐键；缺失或留空时暂停该套餐代充。没有默认报价，不读取已移除的 gpt_plan_prices，也不使用 USDT service_fee 代替。该金额用于准备卡片余额，实际支付以原订单为准；修改地区或平台价格变化时应同步核对配置。配置保存到现有 app_config，无需新增环境变量，升级不会猜测填充历史报价。

“刷新本地记录”展示已保存的卡台成功订单次数；“同步卡片与订单”分页读取 `getSubscriptionList`，对未入账订单调用 `getSubscription` 核对原单，再同步卡片资料和处理退役。需要 `subscriptions:read`。列表缺少卡 ID 时仅使用原订单的明确卡片关联或详情卡 ID；仍无法确认时列为待核对，不按金额、时间、邮箱或尾号猜测。订单同步失败保留已有计数并显示未完全同步，卡片资料仍继续刷新。历史订单网络查询不持有全局选卡锁。

“查看交易”保留 `cardTransaction` 完整分页、授权 ID 去重和脱敏展示，只供对账；不会修改成功会员订单数。“实时选卡预检”和并发模拟按停用记录、平台状态、占用和资金资料判断，不按成功次数限制卡片，不写数据库、不预占或操作资金。

启动自动新增 `successful_order_count` 和 `orbitcard_successful_orders`。历史补记只读取已保存且能验证来源与归属的卡台成功响应，不看本地任务成功/失败标记；无证据记录等待从卡台重新读取，不用旧授权数量替代。启动补记可重复执行，不重置已有计数。卡台之外、API 不可见或无法关联卡片的历史订单无法自动统计；上线后在后台执行“同步卡片与订单”并核对 `order_sync.complete` 和待核对记录。`complete` 只覆盖本次 API 可见的订单，不代表网页等全部渠道均已统计；当前 API 查不到的网页订单不能凭截图或本地成功标记直接加次数。

## 平台 API 与权限

需要核对实际接口字段时，可在服务器项目目录执行以下只读命令（将卡 ID 换成目标卡）：

```bash
docker compose exec -T app node scripts/inspect-card-transactions.cjs 19531519
```

输出交易 ID、类型、原始状态、金额及币种，不输出完整卡号、CVV、密钥或个人信息。最后可加页码，例如 `19531519 2`。此命令不写计数、不删卡、不调用订阅或资金接口；未知状态应据输出核对后补充明确映射，不能当作成功或零次。

沿用 HTTPS 和 HMAC V1 凭据。除原有 subscriptions:read/create、account:read、cards:create/read/fund、products:read 外，卡池删卡需要 cards:manage；会员订单同步计次需要 subscriptions:read，消费授权及资金流水对账需要 transactions:read。

| POST 接口 | 用途 |
| --- | --- |
| getCardList | 完整卡片库存 |
| cardDetail | 脱敏状态和余额 |
| cardTransaction | 读取完整分页统计成功消费授权，指定页明细用于对账 |
| getProductCode | 产品、库存、最低首充和最低留存余额；不提供套餐付款报价 |
| getAccountBalance | 账户可用余额 |
| createCard | 管理员手动申请、卡片错误补开或原身份确认申请；product_code、amount:20.00、quantity:1，固定幂等键 |
| rechargeCard / getCardFlow | 按套餐全额补款及原资金订单确认 |
| deleteCard | 仅确认已持久化的历史退役意图，固定幂等键；成功次数与卡池数量不触发新的删卡 |

API 约定见 [平台协议](../api/Orbitcard-Open-API-V1.md) 和 [订阅协议](../api/orbitcard-subscription-api-v1.md)。HTTP 429 使用账户级限流等待和 Retry-After；权限不足、未知返回值和资金不足会停止相关动作，保留日志供核对。

产品接口按当前 `data.list` 读取产品、库存和最低金额。产品信息由手动开卡和支付准备内部按需读取，管理员无需先查询产品才能申请或支付。后台配置通过 `/api/admin/orbitcard/products` 读取真实产品与 BIN 供多选，也可在“调试与日志 → 接口查询”核对 `getProductCode`。套餐 USD 配置只用于实际代充准备资金。只读预检维护摘要不再保留 `capacity_limit`、`auto_refill`、`open_count`、`opening_amount`，并发统计不再返回 `summary.opening`；现有卡选择、补款、等待和退役提示继续提供。

## 本项目管理 API

| 接口 | 行为 |
| --- | --- |
| GET /api/admin/orbitcard/cards | 本地卡片快照、successful_order_count 统计、availability_basis、usable 与 disabled_* 停用记录，以及独立的 authorization_count、开卡和补款记录 |
| GET /api/admin/orbitcard/products | 卡台实时产品、渠道及 BIN 多选目录 |
| POST /api/admin/orbitcard/cards/:cardId/availability | 二级验证后人工停用或恢复，参数 disabled、reason |
| POST /api/admin/orbitcard/cards/sync | 刷新平台卡片资料和成功会员订单记录、处理退役，不自动开卡 |
| POST /api/admin/orbitcard/cards/apply，Body `{}` | 二级验证后为共享卡池申请一张卡，或确认唯一原手动申请；申请冲突或原删卡未确认时拒绝，不接收旧 `plan_type` |
| GET /api/admin/orbitcard/cards/:cardId/transactions?page=1 | 完整读取授权流水独立对账，并展示指定页最多 50 条脱敏交易 |
| POST /api/admin/orbitcard/issues/refresh | 核对可恢复的原开卡与补款记录；无可确认身份或仍有归属异常的记录继续保留，不恢复会员支付 |

## 验证

运行 npm test。覆盖平台成功结果校验、失败/未知/本地成功不计数、原订单去重、并发结算与回滚、历史迁移和分页同步、卡片归属、独立授权对账、停用与人工恢复、补开唯一性、原资金对账和换卡重试。测试使用模拟 MySQL 和卡台，不执行真实开卡、支付或删除；实际部署仍需核验数据库迁移及 API 权限。

## 故障代码与处理措施

核对日期：2026-11-16。依据项目内的 [平台协议](../api/Orbitcard-Open-API-V1.md#错误与限流)、[订阅协议](../api/orbitcard-subscription-api-v1.md#常见错误) 及其「创建订阅」「结果待确认」「小助手错误响应」章节。下面覆盖这两份协议已公开的错误码，并补充本项目识别的卡片错误、排队错误和未完成状态。平台没有公开完整的 `failureCode`、`relay_*` 或通用错误信封业务码枚举，因此不能将此表视作卡台全部内部错误的清单。

以下规则已接入 API 诊断、订阅提交/查询、自助和管理员结算、后台恢复、开卡及补款确认。自动流程与仍需人工执行的动作见本节最后的对照表；错误提示或动作分类本身不能作为新的扣款授权。

### 判定顺序与重试边界

1. 同时记录接口名称、HTTP 状态、顶层 `code`、`request_error.source/code/upstream_code/submission_outcome`、原订单身份及脱敏失败说明。不同层级的代码分别解析，小助手的 `upstream_code=40030` 不能当作顶层平台码。
2. 先核对订单身份和来源。HTTP 200、`code=0`、本地 `task_status=failed` 都不足以判断订阅结果。仅使用归属一致的已验证上游终态；查询失败、缺字段和身份不匹配保留原记录。
3. **确认卡片问题**：归属一致的原订阅明确失败且命中卡片分类，或本次创建返回 `59005`，才持久化停用原卡并登记补开。查询错误和小助手错误不触发停卡。卡池补开不重置支付尝试次数。
4. **确认未受理**：创建响应明确 `submission_outcome=rejected` 后，先修复 Session、配置或授权等原因，再按正常流程创建新的尝试身份；`59005` 走卡片替换流程。不要修改原订单正文后复用原身份。
5. **受理未知**：`submission_outcome=unknown`、缺失或不可识别时，保留原卡占用及原订单，仅确认原单。订阅查询用原 `task_no/client_order_no`；开卡按契约用原 key、原 Body、同一平台身份重放；补款有原 `order_no` 时只读原流水，无号转人工核对。每次请求生成新时间戳、Nonce 和签名。
6. **重试查询与重试支付分别计数**：查询退避不会产生新支付；支付每条业务链最多 3 次（首次加 2 次续试），不能通过换卡、补开、重启或人工恢复重置。超过重试额度转售后核对，最终一次卡片失败仍可补充卡池，但不能因此再次支付。

### HTTP 与通用平台错误

| 代码或信号 | 对应措施 | 卡片处理 |
| --- | --- | --- |
| HTTP `400`；顶层 `11000` | 检查 Body、Query、字段类型、金额格式及幂等键长度。修正前停止发送同样请求；涉及已有申请时先找回原正文。`11000` 是协议公开的参数错误示例。 | 不据此停卡 |
| HTTP `401` | 管理员核对 API Key/Secret、服务器时间、签名原文、出口 IP 白名单及 Nonce。修复后用新签名确认原单，原业务幂等键保持不变。 | 保留已有占用 |
| HTTP `403` | 检查对应 Scope，例如 `subscriptions:create/read`、`cards:create/read/fund`、`products:read`、`transactions:read`；补齐权限后继续原操作。 | 不据此停卡 |
| HTTP `404` | 按接口区分卡片不存在/不属于当前账户与订阅记录不存在。核对平台、账户、卡 ID 和订单号；卡列表缺失的卡不参与本次选卡，已有关联订单保留待核对。 | 不凭一次查询失败持久化停卡或释放占用 |
| HTTP `409`；顶层 `30004` | 幂等冲突：恢复原 key 与原 Body，核对是否串用了另一笔订单身份。无法找回时人工核对。不能靠换 key、改金额或产品绕过冲突。 | 不换卡重付 |
| HTTP `413` | 原始 Body 超过平台 1 MiB；检查重复包装或异常字段。保留完整必要 Session，避免截断 token；本客户端发送上限另为 256 KiB。 | 不停卡 |
| HTTP `429` | 至少等待 `Retry-After` / `retry_after_seconds`，串行确认原记录并退避；降低同账户请求并发。没有等待值时采用本地退避。 | 不停卡，不开新单绕过限流 |
| HTTP `500` | 内部处理或上游调用失败。只读请求可退避重试；已发送写请求按结果未知确认原记录，持续异常交管理员核对。 | 保留原卡与资金记录 |
| HTTP `502` | 订阅/小助手可能使用此状态包装上游失败；继续读取 `59018`、`request_error` 和受理结果，不能只凭 HTTP 判未受理。 | 不据此停卡 |
| HTTP `503` | 平台 Nonce/限流存储或服务暂不可用，本地并发保护也可能返回此状态。等待恢复并确认原记录。 | 不停卡 |
| 无响应、断网、超时，或 HTTP `408/504` 等未单列的传输错误 | 归为结果未知；保留原身份和请求证据，按接口的恢复方式处理。超时不是未扣款证明。 | 保留原占用 |
| 未知 HTTP / 未公开的非零平台码 | 保存脱敏诊断信息并核对接口、受理状态及原记录；没有明确证据时进入人工核对，不猜测成功或失败。 | 不自动停卡或重付 |

### 订阅平台业务码

| 顶层 `code` | 含义 | 对应措施 |
| --- | --- | --- |
| `59001` | 服务未启用或暂停接单 | 暂停新增订阅，管理员核对服务开关；已有订单继续原单查询与收尾。 |
| `59002` | 不支持的套餐 | 刷新套餐列表，核对 `plan_type` 与已上架套餐；修复选择后再发起，不能自动换成其他价格档位。 |
| `59004` | Session 无效 | 要求用户重新登录目标账号并提供最新完整 Session，核对账号一致；不靠换卡解决凭据问题。 |
| `59005` | 本次创建所选卡不可用 | 持久化停用该卡，保存原任务与错误；按已选渠道和 BIN 登记一次补开。卡片就绪、Session 有效且支付额度未耗尽时继续支付。 |
| `59007` | 未确认支付授权 | 核对真实授权和请求 `authorized`，取得授权后重试；不能把卡片标成故障来跳过授权。 |
| `59008` | 档位未配置 | 管理员检查卡台档位是否启用及配置完整；同时核对本地套餐支付金额，修复后再执行。 |
| `59009` | 订单不存在 | 核对 `task_no/client_order_no`、平台及 API 账户；停止无效主动轮询并转人工核对。曾发送创建请求时，查不到订单不足以证明未受理。 |
| `59013` | 卡台上游密钥未配置 | 联系卡台管理员修复上游凭据配置；暂停新增订阅，不通过换卡处理。 |
| `59015` | 服务费超过 `max_service_fee` | 刷新实际服务费并向管理员展示差额；管理员确认后修改上限，不自动抬高上限。 |
| `59016` | 客户处理中订单达到上限 | 降低并发、继续确认已有订单，待活动名额释放后再提交；不创建多个身份争抢名额。 |
| `59018` | 本次请求或查询异常 | 按下表进一步分类。只有创建明确 rejected 才允许修复后新尝试；unknown、查询异常或仅本地 failed 一律先确认原单。 |
| `59019` | 管理员核验写接口已停用 | 停止调用旧核验写接口，改用原订单查询及只读审计。后台“恢复使用”仅修改卡片状态，不能把订阅人工改成成功。 |

除本次创建的 `59005` 或另外取得已验证卡片失败证据外，上述平台码均不直接触发卡片停用。卡台账户资金不足的通用业务码未公开：先核对账户余额、费用及原资金订单；不能将账户余额不足等同于支付卡余额不足。

### 请求异常与订阅上游拒绝

| 字段或代码 | 对应措施 |
| --- | --- |
| 创建 `request_error.submission_outcome=rejected` | 保存明确拒绝证据；按实际原因修复后再走新尝试。Session/配置类拒绝不补卡。已有支付重试历史的任务仍受原重试额度和售后锁约束。 |
| `submission_outcome=unknown`、缺失或未知值 | 保留原请求、卡片与业务占用，继续确认原单；不换 key 重付。 |
| `request_error.code=relay_query_busy` | 同单查询租约繁忙；串行查询，遵循返回等待值，避免多页面/多任务同时轮询。 |
| 其他 `relay_*` | 文档未给完整枚举。按 source、受理状态、归属和上游终态处理；持续异常人工核对，不能根据名称猜测已失败。 |
| 订阅 `upstream_code=40027` | 重新登录目标 ChatGPT 账号获取最新完整 Session。若本次提交仍为 unknown，先确认原单，再处理新的付款尝试。 |
| `request_error.code=assistant_invalid_response` | 小助手结果不完整或不匹配；停止采用本次结果，核对账号、目标套餐、金额和币种。查询可退避重试；自动续费操作先查询实际 `willRenew`。 |
| 归属不匹配、缺少可信终态、`subscription_succeeded=null` | 停止自动履约或新付款，保留原记录转人工核对。不能据此退款、释放卡片占用或计为订阅失败。 |

### GPT 小助手上游业务码

这些代码读取自 `request_error.upstream_code`，常由 HTTP 502 / 顶层 59018 包装。它们属于账号、报价或续费操作，**均不直接触发支付卡停用、补开或订阅换卡**。协议将部分代码合并说明，下表保留同样的分组，不臆造逐码的更细含义。

| `upstream_code` | 文档定义的范围 | 对应措施 |
| --- | --- | --- |
| `40030 / 40031 / 40032 / 40033` | Session、登录 Cookie、续费参数或目标套餐无效 | 按当前接口及安全错误说明修正参数。刷新 Session 的接口需要 sessionToken / session_token / 登录 cookies，只有 accessToken 不够；`enabled` 用布尔值，`targetPlan` 使用小助手套餐代码。 |
| `42230 / 40934` | 登录失效或目标账号不匹配 | 获取该目标账号的最新完整 Session，重新核对 email/accountId，停止沿用不匹配凭据。 |
| `42231 / 42232` | 非网页订阅或渠道无法确认 | 刷新账号信息核对 `paymentChannel`；App Store/Google Play 订阅通过原渠道处理，渠道未知时人工核对。 |
| `40935 / 40936` | 已有目标套餐或目标为降档 | 提示当前套餐与目标套餐；若已满足需求则结束，确需升级由用户选择支持的更高档位后重新报价。 |
| `40937 / 40938 / 40939` | 无有效订阅、状态或档位无法确认 | 重新查询账号。无有效订阅时停止升级报价流程；未知状态保留为未知，不推断套餐。 |
| `42233 / 40940 / 40941` | 无购买资格、未结清账单或暂不支持升级 | 向用户显示对应的安全原因，先处理账号资格或未结账单，再查询资格与报价；不自动扣款清账或代选套餐。 |
| `50233` | 报价缺少应付金额或币种 | 拒绝采用该报价，退避重查，持续异常联系卡台；不得当作 0 元，也不以标价代替实际应付金额。 |
| `40930 / 40931 / 40932` | 续费不可用、进行中或结果未确认 | 先查账号与 `willRenew`。达到目标则完成；未知时等待核对，不能马上重复提交续费开关。 |
| `42900 / 50331` | 上游限流 | 遵循 `Retry-After`，降低查询频率；同用户多个 Key 共享限制，不能靠轮换 Key 绕过。 |
| `50230 / 50231 / 50232 / 50330` | 上游请求失败、拒绝访问、无有效最新 Session 或服务不可用 | 结合当前操作和安全说明区分：查询/服务故障退避重查；认证或 Session 问题重新登录；持续拒绝访问交卡台核对；续费写操作先查实际状态。 |

### 本项目识别的卡片失败

下列字符串是 `src/orbitcard/orbitcard-card-failure.js` 当前识别集合，**不是卡台公开的完整枚举**；大小写、驼峰、空格和连字符会先规范化。只有已验证失败的订阅才能据此停卡；创建 `59005` 会映射成 `card_unavailable`。不能从任意接口的 `msg` 提取这些词便停卡。

| 本地识别的 `failureCode` | 对应措施 |
| --- | --- |
| `card_error / card_declined / do_not_honor / payment_method_declined` | 记录拒付，持久化停用原卡并补开；保留拒付证据用于管理员判断渠道质量。 |
| `card_unavailable / card_not_available / card_invalid / invalid_card / incorrect_card` | 停用并补开；管理员同步核对卡 ID、资料及平台状态，排除资料错误后可人工恢复。 |
| `card_expired / expired_card` | 停用并补开；旧卡恢复前须确认平台已提供有效卡片资料。 |
| `card_blocked / card_restricted / restricted_card / lost_card / stolen_card` | 停用并补开；管理员核对冻结、限制或挂失状态，解除原因后再考虑人工恢复。 |
| `card_not_supported / unsupported_card / transaction_not_allowed` | 停用并补开；管理员检查产品、BIN、支付地区及商户支持情况，必要时调整候选渠道/BIN。自动轮换不保证避开原 BIN。 |
| `card_limit_exceeded` | 停用并补开；核对平台实际交易限额，不恢复按本地成功次数淘汰卡片的规则。 |
| `insufficient_funds` | 仅作为已验证订阅的卡片失败处理：按当前要求停用并补开，同时检查报价、最低留存、余额同步与扣款。卡台账户不足、服务费不足和未完成补款分别对账。 |
| `incorrect_cvc / invalid_cvc` | 停用并补开；管理员通过卡台核对资料，日志不保存 CVC/CVV。 |
| 未命中代码，但失败说明明确指出卡片拒付/无效/过期/冻结/受限/余额不足或 CVC/CVV 错误 | 在不存在明确非卡片原因时按卡片错误停用；保留脱敏证据供复核。否定文案、链接内容及无卡片语境的资金不足不匹配。只有失败终态可走此分支，不能靠说明文本推断原订单已终结。 |
| 未知代码且说明不明确 | 保留失败详情，不自动标记卡故障；停止进一步支付，进入售后核对，由管理员确定是账号、商户、渠道还是卡片问题，再决定是否人工停用。 |

补开选择受管理员多选 `product_code` 与 BIN 的交集约束：刷新库存、最低首充及账户资金后才创建，每张首充 20 USD。同一原卡、同一失败任务只登记一笔补开；该申请明确失败后保留记录，不循环创建新申请。管理员处理原因后可正常手动开卡；人工停用自身不触发补开。

### 无错误码但必须处理的状态与本地故障

| 状态或本地代码 | 对应措施 |
| --- | --- |
| 开卡 `created/validating/balance_locked/processing/pending_confirm` 或 `completed=false` | 原 key、原 Body 确认同一申请，遵循重查间隔；界面显示处理中，不把等待超时当失败。 |
| 开卡 `success` 但无有效 `card_id`，或未知状态 | 不交付、不推断卡归属；保留原申请重查，持续异常人工核对。 |
| 开卡 `failed/refunded` 且确认完成 | 记录该申请终态，核对费用与退款/解冻流水；不重复退款，不自动无限补开。 |
| 补款待确认、成功但余额未同步 | 保留卡片占用，每至少 5 秒只读核对原资金号与余额，更长 Retry-After 优先。等待窗口最多 120 秒，之后转 `funding_review` 继续对账，不重复补款。 |
| 补款无原资金号、金额或归属不一致 | 转人工核对并保留原意图，不更换金额/key 重充。 |
| `awaiting_captcha` 且 `captcha.status=pending` | 展示当前完整验证入口，用户完成后继续查原订单。链接过期时查询最新验证任务，url=null 时联系卡台配置；链接关闭、已提交验证或字段暂时消失均不代表支付成功。 |
| `fee_status=charge_pending/charge_failed` | 订阅结果单独判断。服务费待收/失败不触发换卡或重新订阅；核对卡台服务费事项及账本，不能假定充值/刷新会重启已结束收费。 |
| `subscriptionCancelled=false/null` | 单独展示续费取消结果，查询账号实际续费状态；null 表示未知。不能因此把已成功订阅改为失败或再次付款。 |
| `PAYMENT_QUEUE_FULL` | 等待位已满，提示 10 分钟后再试；不释放其他任务的卡。 |
| `PAYMENT_QUEUE_TIMEOUT` | 已等待 30 分钟，本次等待中的支付未提交；提示 10 分钟后使用原业务入口及最新 Session 重试。有历史支付或未决资金的任务仍按原锁定规则处理。 |
| `PAYMENT_QUEUE_STOPPED` | 服务停止/重启导致排队结束；恢复后使用原 CDK 或管理员 request_id 和最新 Session 继续，保留历史尝试。 |
| 选卡原因 `busy / previous_payment_attempt / missing_from_platform_list` | 分别表示卡被占用、本支付链已使用、实时列表缺失；不是支付失败码。等待占用释放、按重试排除旧卡、同步核对缺失卡，不能直接据此判卡故障。 |
| 选卡 `card_error_disabled / retiring / inactive / status_unconfirmed / invalid_detail / invalid_payment_data` | 分别核对本地停用、原退役、平台状态、实时资料和金额配置；跳过不合格卡，已有归属的卡保留核对，不以历史成功次数覆盖判断。 |

### 程序执行与人工处理边界

| 能力 | 当前情况 |
| --- | --- |
| 卡片失败停用、`59005`、持久化补开及人工恢复 | 已实现；失败结算与停用原子提交，平台同步不会覆盖停用。人工操作需原因、二级验证和审计，仍有占用不能修改，退役中的卡不能直接恢复。 |
